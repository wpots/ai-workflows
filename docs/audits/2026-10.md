# AI Stack Review — October 2026 Follow-up

Status check on the [July 2026 review](2026-07.md), ten weeks
on. Measured against `gitlab/main` at plugin 2.5.0 (2026-10-07) and the
ecosystem as of 2026-10-07. Produced from a repo read, a multi-agent web
research run with adversarial claim verification, and direct checks of the
Claude Code docs.

**How to read this:** TL;DR → task status → what changed outside → re-ranked
plan → delivery status → decisions only the maintainer can make → confidence →
sources. The plan stays as written; [Delivery Status](#delivery-status) says
how far it got.

---

## TL;DR

1. **Most of the July plan shipped.** 12 of 18 tasks are done, plus work the
   review never asked for: CLI-first service access with a deny hook, a
   post-merge release flow, an unenforced-policy budget, 38 skills (was 29).
2. **The open items are still the right ones, but three of them changed shape
   because the platform caught up.** Build less, configure more:
   - **T4 eval harness**: Claude Code now ships `claude plugin eval`. Do not
     write a runner. Convert the 12 existing eval files to its format and gate
     CI on it.
   - **T5 CI agent lane**: GitLab's own Code Review Flow and Fix-pipeline flow
     are GA and run Claude Sonnet 5.5. Pilot and measure them before building
     anything.
   - **Stop-hook retrospective**: was blocked on "no observable predicate".
     Agent-type Stop hooks can now read the transcript, which is that
     predicate.
3. **One cheap new lever for T18:** Claude Code runs a skill named `verify`
   before every commit. Plugin skills do not count, so it has to be a
   project-level skill that `setup-ai-workflows` emits.
4. **Downgrade T10.** Adding brainstorming/writing-plans skills costs listing
   budget in every session; only `systematic-debugging` is a real gap, and it
   should prove its lift with an eval first.

## What Changed Outside (since 2026-07-29 unless marked)

### Claude Code

- **`claude plugin eval`** (v2.1.269, 2026-09-11). A first-party eval runner
  for plugins and skills. Each case runs three times with the plugin and three
  times without, so you get WITH, W/OUT and the delta the plugin contributed.
  Graders: `regex`, `tool_used`, `tool_order`, `file_exists` (free) and `llm`,
  `baseline` (judged, two-of-three vote). A `tool_used: Skill` grader is the
  built-in trigger/routing eval. CI mode: `--json`, `--threshold`,
  `--trust-plugin`, pinned `--model`/`--judge-model`, `--max-cost-usd`, exit
  codes 0/1/2. Plugin MCP servers are mocked from Markdown files by default.
  - **Not compatible with our files**: it reads `evals/<case>/prompt.md` plus
    `graders/*.md`, not skill-creator's `evals/evals.json`. The docs say
    neither tool reads the other's files.
  - **Isolation matters for us**: runs load no `CLAUDE.md`, user settings,
    hooks or other plugins. Skills that lean on the ambient layer or on
    `glab`/`jira` need fixtures, mocks or a `scaffold_script`. Granting Bash
    on Linux needs bubblewrap + socat on the runner.
- **`/skill-doctor`** (v2.1.252). Per-skill context cost, never-invoked skills,
  unused plugins. Works headless with `-p`. This is the profiling tool F10
  asked for.
- **Description listing cap**: `description` + `when_to_use` are truncated at
  1,536 characters in the skill listing. `paths:` frontmatter limits
  auto-activation to matching files — a fit for stack-specific skills
  (`payload-jobs`, `migration-check`, `datocms-migration`).
- **`verify` skill convention** (v2.1.286, 2026-09-30). When a session starts
  with a skill named `verify`, the commit instructions tell Claude to run it
  before every commit except docs- or tests-only ones. **Plugin skills do not
  count** — only enterprise, personal, project, nested or additional-directory
  skills. It is model guidance, not a hard gate.
- **Hooks**: all five hook types (`command`, `http`, `mcp_tool`, `prompt`,
  `agent`) work on `Stop` and `SubagentStop`, and plugins can ship them.
  Every hook gets `transcript_path`; `Stop` adds `stop_hook_active`,
  `last_assistant_message` and `stop_reason`. Agent hooks (experimental) can
  Read/Grep/Glob, so they can inspect the transcript before returning
  `decision: "block"` with a `reason`.
- **Claude Mods** (v2.1.287, 2026-10-01). Plugins can register JavaScript
  function hooks that gate or modify engine behaviour, with a
  `claude plugin test` runner. Six days old at the time of writing: watch.
- **Org distribution** (`/docs/en/plugins/org`). Managed settings can
  force-register a marketplace (`extraKnownMarketplaces`, `git` source works
  with GitLab) and force-enable plugins (`enabledPlugins`). Stable and
  early-access channels are two marketplaces on different refs. OpenTelemetry
  events `claude_code.plugin_installed` / `plugin_loaded`. There is still no
  cryptographic plugin signing; trust is source allowlisting
  (`strictKnownMarketplaces`).
- **Headless/CI plugin loading**: `CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1` makes a
  `-p` run wait for plugin install; `CLAUDE_CODE_PLUGIN_SEED_DIR` pre-seeds a
  read-only plugin cache in a runner image.
- **Routines** (research preview). Cloud scheduled/API/GitHub-triggered runs.
  Repositories must be **GitHub**; routines belong to one personal account and
  are not shared; minimum interval one hour. Poor fit for GitLab client
  projects and for a team-owned sweep.
- **AGENTS.md**: Claude Code reads `AGENTS.md` natively when no `CLAUDE.md`
  exists.

### GitLab

- **Code Review Flow** (Duo Agent Platform). GA since 18.8 (Jan 2026, so it
  predates the review), Free tier via GitLab Credits since 18.10. New since
  July: model moved to Claude Sonnet 5 (2026-08-06) and Claude Sonnet 5.5
  (2026-10-05); push-triggered re-reviews in 19.5. Config lives in the repo:
  `mr-review-instructions.yaml` and `.gitlab/duo/mr-review-automated-rules.yaml`,
  cascading group → project. Limits: disabled by default, needs Duo Core or
  credits plus runners tagged `gitlab--duo`, context capped around 800 KiB,
  it **does not read AGENTS.md or SKILL.md**, and its approval does not count
  toward required approvals.
- **Fix pipeline flow** GA since 18.8 — the platform's own pipeline triage.
- **Claude Code Agent by GitLab** (external agent) GA since 18.8, with a
  "Merge request ready" trigger GA in 19.1 and GitLab-managed credentials.
  Anthropic's GitLab CI/CD page still says beta and links a support issue that
  was closed in December 2025; GitLab's own docs are the current source.
- 19.3 (2026-08-20): "Resolve with GitLab Duo" for review threads GA; Duo CLI
  plugins as an experiment, reading `.claude-plugin/marketplace.json` (skills,
  commands and MCP only — no hooks).
- 19.4 (2026-09-17): MCP tools that trigger a pipeline and read a failed
  job's trace; per-user credit caps. *(Press release; not independently
  verified.)*

### Standards

- **Agent Skills** (SKILL.md): Cursor, GitHub Copilot, Codex and Gemini CLI
  all document native support. Cursor also reads `.claude/skills/` directly and
  ships `/migrate-to-skills` to turn its rules and commands into skills. The
  spec has no owner or version field; that goes in `metadata`.
- **Agent Plugins 1.0** (2026-08-06): a vendor-neutral plugin packaging spec
  stewarded by Amazon, Cursor, Microsoft, OpenAI and Vercel. Anthropic is not
  on it and Claude Code is not a client; GitLab Duo CLI supports it since 19.4.
  Skills are converging; plugin packaging is forking. Watch, don't adopt.

### Ecosystem stacks *(primary sources, but the verification pass ran out of budget — treat as single-source)*

- **obra/superpowers** v6.3–6.4.2 (Aug–Sep): brainstorming ceremony now scales
  to task size, plans require review before execution and record decisions
  instead of full code, a new `diagnosing-superpowers` skill analyses failed
  sessions, and the plugin dropped its `CLAUDE.md` pointer for `AGENTS.md`.
  Its eval harness moved out of the plugin after it broke installs.
- **Every compound-engineering**: ~20 releases since late August. Learnings
  must now name their **retirement condition** and capture is gated on durable
  knowledge (v3.29.0). Review promotes a finding only when a cross-model peer
  agrees. It ships its own skill-eval/optimize lane and still packages per host
  (14 hosts) rather than relying on the standard alone.
- **Anthropic engineering posts** (claude.dev): verification skills had the
  most measurable effect on output quality; skill usage is logged with a
  PreToolUse hook to find under-triggering skills; skills are promoted from a
  sandbox folder into the marketplace by PR; `/claude-api build-eval` and
  `/claude-api hillclimb` design and iterate evals.

### Evidence on headless AI review *(pre-July, not in the July sources)*

- Atlassian RovoDev (ICSE'26): comment resolution rate 38.7% vs 44.5% for
  human comments; median PR cycle time down 30.8%. Thumbs-up/down feedback was
  useless; behavioural resolution rate is the metric.
- An in-the-wild study of 31k CodeRabbit review/feedback pairs: 56% rejected,
  mostly false positives, redundant or out-of-scope comments.
- A 2026 literature synthesis rates the effect of fully automated review on
  quality and security as contested.

## Decisions Only the Maintainer Can Make

Answered 2026-10-08:

- **GitLab licensing.** The `greenberrynl` group is on Premium with 9 seats;
  Duo Core and the Duo Agent Platform are on; foundational agents are off by
  default. No upgrade is planned. Code Review Flow works on Duo Core and is
  billed in GitLab Credits at 4 reviews per credit; Premium users get
  included credits monthly, and on-demand credits ($1 each) only apply after
  someone accepts usage billing terms. Rank 5 stays in scope as a pilot on
  the current tier.
- **Claude plan.** Greenberry is on Claude for Teams. Server-managed settings
  are available, but only an Owner or Primary Owner can edit them, at
  claude.ai/admin-settings/claude-code. The maintainer's role is member.
- **Non-Claude tools.** The team uses Claude and Codex; Cursor is being phased
  out. T3 narrows to two targets. Codex reads SKILL.md from `.agents/skills`
  (repo) and `~/.agents/skills` (user), while `scripts/sync.sh` still copies
  to `~/.codex/skills/custom`; on the maintainer's machine that copy holds 29
  skills against 38 on main. The Cursor adapters and the `.cursor/mcp.json`
  emission can go.
  - *Corrected 2026-10-28:* the sync target is not wrong. Codex 0.164 also
    scans `$CODEX_HOME/skills` (its `codex-home-skills` root, next to
    `~/.agents/skills`; read from the binary, not from a live run). The 29
    against 38 is a copy that was not re-synced. And "two targets" overstated
    the record: Copilot stayed supported until the 2026-10-28 answer below.
- **F3, commands in the plugin.** Claude Code merged commands into skills: a
  command is model-invocable by default and a same-name skill wins. 14 of the
  17 commands shadow a skill and are dead weight in Claude while still being
  maintained; `review-code` duplicates `code-review` under another name, so
  both compete for the same trigger. Their remaining audience was Cursor,
  Copilot and the Codex fallback, and Codex now reads skills. Recommendation:
  keep `safe-kill-port` and `new-device-setup`, drop `review-code`, and retire
  the twin runbooks once Codex is confirmed to load the skills.
  - *Still open on 2026-10-28.* With Copilot out, the runbooks serve only Codex
    and the fallback rows of `CLAUDE.md`. The Copilot retirement leaves the
    runbooks' Copilot wording to this decision.

Answered 2026-10-28:

- **Copilot out.** Claude and Codex are the supported tools. Recorded as the
  2026-10-28 amendment of `docs/skills-first-migration-plan.md`; the retirement
  is three backlog slices under rank 7. `.github/` files that synced projects
  already hold are left alone.

Answered 2026-10-29:

- **No `paths:` on `rules/project.md`.** Scoping it to code files would keep
  its 2.8k tokens out of sessions that touch no code, but the patterns of a
  user-level rule resolve against the session's primary working directory.
  Measured on Claude Code 2.1.296 (2026-10-28): a session in the main checkout
  loads the rule when it reads a `.ts` file there, and does not load it when it
  reads the same file in a sibling worktree, even one added with `--add-dir`.
  The memory docs say the same: only a session started in the worktree, or
  moved there with `/cd`, picks the rule up. The worktree flows keep the
  session in the main checkout and write under `~/.worktrees/`, so they would
  lose the coding rules without any signal. The rule stays always loaded.

Still open:

1. **CI spend — decided 2026-10-08: manual for now.** Evals and delivery
   metrics run locally on the maintainer's Team seat; no CI credential, no
   scheduled lane. The CI eval job stays parked; since 2026-10-13 routing evals
   run on the maintainer's seat before a skill MR instead (!183). Revisit once
   local runs have produced a few weeks of real `costUsd` figures.
2. **`run-checks` CI parity.** The CI-job-to-local-command mapping is the
   blocker under pipeline triage. *Delivered 2026-10-21 (!262).*
